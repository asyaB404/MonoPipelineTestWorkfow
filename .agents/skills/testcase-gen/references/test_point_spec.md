# 测试要点规范

## 一、文档清洗

在分析文档前，必须先清洗内容，去除以下干扰：

### 需跳过的章节（元信息）
- 文档简介、读者对象、文档目的、版本历史、修订记录
- 文档说明、适用范围、参考文档、术语定义、名词解释
- 目录（TOC）

### 需跳过的表格
- 已有测试要点表格（含"测试要点/CheckList/优先级/风险等级/功能模块/子功能点/测试类别"等表头）
- 版本控制表格（含"密级/版权/文档编号/作者/编写人/审核人/批准人/创建日期/完成日期/备注"等）
- 封面信息（"版权所有"、"不得复制"）

### 清洗规则
- 遇到元信息标题 → 跳过整个章节直到下一个同级或更高级标题
- 遇到测试要点表格行（含 `|` 且含表头关键词）→ 跳过所有连续的表格行
- 遇到元信息表格行（含 `|` 且含版本控制关键词）→ 跳过表格行及后续空行
- 遇到目录标记 → 跳过直到下一个标题

## 二、Map-Reduce 两阶段生成

### 阶段一：提取模块列表（Map）

用全文一次性识别所有功能模块和子功能点，输出格式：

```json
[
  {
    "name": "登录系统",
    "sub_features": [
      {"name": "账号密码登录"},
      {"name": "手机验证码登录"},
      {"name": "第三方登录"}
    ]
  }
]
```

要求：
- 每个模块提取其所有子功能点
- 子功能点粒度要细，能独立生成测试要点
- 不要遗漏文档中任何功能描述

### 阶段二：逐模块生成要点（Reduce）

**关键：先提取每个子功能点的上下文。**

对于每个子功能点，从文档中定位其对应的章节段落（从该子功能点标题到下一个同级或更高级标题之间的内容），仅基于该段落生成测试要点，不要混入其他模块的内容。

如果提取的上下文过短（<50字），尝试用父模块名提取。如果短文档（<12000字）且提取失败，可用全文但只关注该模块相关内容。

## 三、游戏类型覆盖维度

根据游戏类型，必须覆盖以下强制维度：

### 休闲SLG放置
1. 挂机放置（离线收益计算、收益上限、回归结算、加速道具）
2. 资源管理（资源上限、溢出处理、多货币并发扣减、防超发）
3. 建筑/升级（升级条件校验、等级上限、升级回滚、并发升级）
4. 联盟/社交（加入/退出联盟、捐献次数上限、联盟战、邮件）
5. 活动系统（限时活动开关、奖励发放、排行榜刷新、时区处理）
6. 付费系统（商城购买、礼包限购、VIP特权、充值回调）
7. 异常&边界（网络断开、数据同步、并发操作、时间篡改检测）
8. 隐含需求（放置感、成长曲线、付费节奏、长期留存）

### MMO/MMORPG
1. 角色成长（等级/转职/天赋、属性计算、成长曲线平衡）
2. 副本系统（难度校验、组队匹配、掉落分配、重置机制）
3. 战斗系统（技能释放、BUFF/DEBUFF叠加、仇恨机制、AOE范围）
4. 经济系统（拍卖行、货币流通、防通胀、交易安全）
5. 社交系统（公会、组队、好友、聊天频道、举报机制）
6. 大世界（地图加载、NPC刷新、资源点争夺、跨服同步）
7. 异常&边界（掉线重连、数据回滚、并发冲突、外挂检测）
8. 隐含需求（沉浸感、社交粘性、付费节奏、防沉迷）

### 模拟经营
1. 经营核心（建筑放置/拆除、员工雇佣上限、营业额计算）
2. 资源链（原材料→生产→销售全链路、库存上限、缺货处理）
3. 顾客系统（顾客AI、满意度计算、差评触发、高峰期并发）
4. 升级扩张（建筑升级条件、解锁新区域、扩建边界校验）
5. 活动/任务（限时任务、节日活动、奖励发放、进度保存）
6. 付费系统（加速道具、装饰购买、高级员工、礼包限购）
7. 异常&边界（存档保护、数据回滚、时间加速检测、并发操作）
8. 隐含需求（经营成就感、数值平衡、付费节奏、长期目标）

### 回合制卡牌/自走棋
1. 卡牌/棋子系统（费用校验、技能触发、羁绊效果、星级合成）
2. 战斗回合（行动顺序、技能优先级、BUFF叠加上限、回合结束结算）
3. 抽卡/商店（概率公示、保底机制、刷新费用、限购校验）
4. 阵容搭配（羁绊激活条件、上阵数量上限、位置限制）
5. 排位/天梯（积分计算、段位晋升、赛季结算、奖励发放）
6. 付费系统（抽卡充值、通行证、礼包限购、概率合规）
7. 异常&边界（断线重连、回合超时、并发操作、数据回滚）
8. 隐含需求（策略深度、抽卡体验、付费节奏、赛季留存）

### Roguelike/休闲肉鸽
1. 随机生成（地图随机性、事件池权重、道具池平衡、种子复现）
2. 永久进度（永久升级保留、死亡重置范围、解锁条件校验）
3. 战斗系统（技能/道具叠加上限、BUFF冲突、伤害溢出处理）
4. 关卡推进（Boss难度曲线、精英房触发率、商店刷新）
5. 存档机制（断点续存、死亡清档、存档防篡改）
6. 付费系统（初始角色解锁、道具包、通行证、礼包）
7. 异常&边界（崩溃恢复、数据回滚、随机种子异常、并发）
8. 隐含需求（随机惊喜感、成长曲线、付费节奏、多周目留存）

### 塔防
1. 防御塔系统（放置/拆除、攻击范围、升级费用、特殊效果）
2. 敌人波次（波次间隔、敌人属性、精英/Boss出现条件、路径AI）
3. 资源管理（金币获取/消耗、建造上限、拆除返还比例）
4. 关卡机制（胜利/失败条件、星级评价、特殊地形、机关触发）
5. 英雄/技能（英雄部署、技能释放、冷却时间、能量消耗）
6. 付费系统（英雄解锁、道具购买、体力购买、礼包）
7. 异常&边界（波次卡死、资源溢出、并发建造、断线恢复）
8. 隐含需求（策略深度、难度曲线、付费节奏、关卡留存）

如果用户未指定游戏类型，默认使用"塔防"的维度（如齿轮滚滚等推塔防游戏）。

## 四、字段定义

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `function_module` | string | ✅ | 格式 `"父模块 - 子模块"`，如 `"登录系统 - 账号密码登录"` |
| `feature_point` | string | ✅ | 从正文识别的**具体子功能名**（2-10字），如"进度条"、"Loading提示文本"、"登录天数"。**禁止**照搬模块名 |
| `sub_module` | string | ✅ | 具体业务场景名（2-15字），如"注册账号"、"密码验证"、"进度条加载"。**严格禁止**写成"XX类"、"异常场景类"、"边界值类"等分类名 |
| `parent_point` | string | ✅ | 可执行的测试操作（10-30字）。✅ "输入超长密码后点击登录" ❌ "登录功能测试" |
| `test_point` | string | ✅ | 具体的边界值/特殊数据/测试条件（5-30字）。✅ "密码长度恰好33位（超出上限1位）" ❌ "验证密码长度限制" |
| `priority` | string | ✅ | P0/P1/P2/P3 |
| `risk_level` | string | ✅ | HIGH/MEDIUM/LOW |
| `description` | string | | 详细描述 |
| `test_conditions` | list | ✅ | 前置条件 |
| `test_steps` | list | ✅ | 操作步骤 |
| `expected_results` | list | ✅ | 预期结果 |
| `boundary_values` | dict | ✅ | 边界值，如 `{"金额": "0, 0.01, 999999"}` |
| `confidence` | float | | 置信度 0~1 |
| `implicit_requirement` | bool | | 是否为隐含需求 |
| `fault_tolerance_scenario` | string | | 容错场景描述 |

## 六、生成规则（逐条严格执行）

### 6.1 穷举原则

**逐条扫描文档，不遗漏任何内容：**
- 文档中每条规则 → 至少 1 条要点
- 每个枚举值 → 单独 1 条 test_point
- 每个状态 → 单独 1 条 test_point
- 每个条件分支 → 至少 1 条要点
- 每个 parent_point（操作）→ 穷举所有相关 test_point（数据/条件）

### 6.2 数值/参数类覆盖

必须覆盖：0、最小值、最大值、最大值+1（超出）、负数（如适用）

### 6.3 输入框类覆盖（逐条，每条单独一个 test_point）

- 空字符串
- 1个字符（最小长度）
- 恰好达到上限长度的字符串
- 超出上限长度1位的字符串
- 合法字符组合（字母+数字）
- 特殊符号（如 !@#$%）
- 纯空格
- 中文字符
- emoji 字符
- SQL注入字符串（如 `' OR 1=1 --`）
- 首尾含空格的字符串

### 6.4 流程类覆盖

- 正向流程：每个关键步骤一条
- 异常中断：网络断开、超时、并发冲突各一条
- 边界值：每个临界值单独一条

### 6.5 生成顺序

1. 先扫描正文 → 识别具体子功能点（feature_point）
2. 按测试场景 → 归纳 sub_module（不能是"XX类"）
3. 再生成 parent_point（操作） → test_point（数据/条件）

### 6.6 后处理规则

生成完每个模块的要点后，逐条检查：
- `feature_point`：如果照搬了模块名或子功能点名，从 `parent_point` 中提取关键词替换
- `sub_module`：如果以"类"、"场景"结尾或超过15字，从 `parent_point` 中提取业务动作归纳
- `test_point`：去除末尾套话词（如"正确性"、"准确性"、"有效性"、"是否合理"）

### 6.7 输出要求

- 严格 JSON 数组，不要任何其他文字
- 每个要点必须包含所有必填字段

## 七、优先级定义

| 级别 | 定义 | 示例 |
|------|------|------|
| P0 | 核心功能，阻塞性 bug 导致系统不可用 | 登录、支付、核心战斗 |
| P1 | 主要功能，影响大部分用户 | 主要 UI 交互、关键流程 |
| P2 | 次要功能，影响部分用户 | 辅助功能、非关键流程 |
| P3 | 边缘场景，影响极小 | 极端边界、低频操作 |

## 八、风险等级定义

| 等级 | 定义 |
|------|------|
| HIGH | 涉及资金、数据安全、核心流程 |
| MEDIUM | 涉及用户体验、性能 |
| LOW | 纯展示、文案类 |

## 九、质量评估

### 评分维度

| 维度 | 权重 | 计算方法 |
|------|------|----------|
| 覆盖率 | 25% | 将文档按语义块分割，检查每个语义块是否被至少 2 个关键词覆盖 |
| 准确性 | 25% | 检查 test_conditions/test_steps/expected_results 三个字段是否 ≥80% 非空 |
| 可执行性 | 25% | 检查 test_steps 和 expected_results 是否都非空且长度>0 |
| 完整性 | 25% | 检查 function_module/sub_module/test_point/priority/description/test_conditions/test_steps/expected_results 八个字段是否 ≥80% 非空 |

综合评分 = 覆盖率×0.25 + 准确性×0.25 + 可执行性×0.25 + 完整性×0.25

### 逐点检查

对每个要点额外检查：
- `function_module` 长度 ≥ 2
- `test_point` 长度 ≥ 5
- `priority` 在 P0/P1/P2/P3 中
- 无缺失必填字段
- 无空字段（空字符串、空列表）
